## 1. 지금 «받은 명함» 은 무엇인가 (사실)
- **PlanQ 명함 링크(/c/…)를 받은 사람이 [내 명함첩에 보관] 을 누른 것만** 들어온다. 직접 입력·종이 명함은 들어올 길이 없다.
- **계정 소유**(saved_name_cards — 워크스페이스와 무관한 개인 명함첩). 팀이 같이 못 본다. 고객(Q sale)과 연결이 없다.
- dev 보관 1건, 운영 0건(기능 미배포). → 지금 형태로는 쓰임새가 거의 없다. Irene 이 «뭔지 모르겠다» 고 한 것이 정확하다.

## 2. 진짜 쓰임새 — 명함은 «관계의 입구»다
B2B 에서 명함을 받는 순간 = 새 고객·새 담당자를 알게 된 순간이다. PlanQ 에서 그 관계가 사는 곳은 **Q sale 고객**이다(CLAUDE.md «고객이 이미 허브다»).
그래서 «받은 명함» 을 개인 명함첩으로 따로 키우지 않고, **고객 정보로 들어가는 입구**로 바꾸는 것을 제안한다.

| 지금 | 제안 |
|---|---|
| 내 계정 > 내 명함 > «받은 명함» 탭 (개인 보관함) | **받은 명함 = 고객으로 들이는 입구.** 들어오는 길 셋 → 확인 화면 → [새 고객으로] / [기존 고객의 담당자로] / [나만 보관] |
| PlanQ 링크로만 들어옴 | ① PlanQ 명함 링크 보관(지금) ② **종이 명함 사진 → AI 가 칸을 읽어 채움** ③ 직접 입력 |
| 고객 정보에 사람 칸이 얇다 | 고객에 **담당자(사람) 명함 칸** — 이름·직함·부서·휴대폰·전화·이메일·주소·명함 사진 |

## 3. 고객 정보에 명함 내용 — 필요하다
- 지금 `clients` 는 **회사 하나 = 사람 하나** 모양이다(display_name·company_name·phone·invite_email + 사업자·청구 담당 칸). 직함·부서·휴대폰/일반전화 구분·주소·명함 사진 칸이 없다.
- B2B 고객은 한 회사에 담당자가 여럿이다(대표·실무·경리). 명함을 받을 때마다 «새 고객» 이 생기면 한 회사가 여러 고객으로 쪼개진다.
- **결정 필요(구조)**: (a) `clients` 에 명함 칸 몇 개만 더함(사람 하나) vs (b) **고객 아래 «담당자» 표 `client_contacts`**(사람 여럿, 대표 담당자 1 = 지금 칸과 사본) — 나는 (b) 를 권하지만 고객·초대·계정 연결·청구 담당·메일 상담 분류가 모두 «고객 = 사람 하나» 를 읽고 있어 범위가 크다 → Fable 판정.

## 4. 종이 명함 사진 공유 → 고객 정보
- 흐름: Q sale / 받은 명함에서 [명함 사진으로 추가] → 폰 카메라·사진 선택 → AI 가 이름·회사·직함·연락처를 읽음 → **사람이 확인·수정**(자동 저장하지 않는다) → 고객으로 등록/기존 고객 담당자로 붙임. 같은 이메일·전화가 이미 있으면 «이미 있는 고객» 으로 묻는다(중복 방지).
- 사진은 고객 담당자의 «명함 사진» 으로 남긴다(EXIF 제거 — v1 과 같은 처리). 원본 저장 여부는 결정 항목.
- 기술 사실: LLM 게이트웨이(services/llm.js, OpenAI)는 지금 **글자 입력만** 다룬다(`capMessages` 가 content 를 문자열로 본다) — 사진 읽기는 게이트웨이 확장이 필요하다. 계량은 Cue 1회. 체험 캡·costGuard 그대로.
- **개인정보**: 명함 사진·내용을 OpenAI 로 보내는 것은 국외 이전이다 — 처리방침에 이미 «AI 기능 국외 이전» 이 있는지 확인하고 없으면 문구 추가. 명함 주인(제3자)의 동의 문제는 «업무상 받은 명함으로 연락처를 관리» 범위(정보주체가 스스로 준 명함)로 본다 — 법적 판단은 Fable/결정 항목.

### 확인한 사실
- 받은 명함 입구는 링크 보관뿐(`routes/name_cards.js` POST /saved). clients 의 «사람» 칸은 세 군데 다른 모양(본인 칸 · billing_contact_* · project_clients.contact_*).

### 결정 1 — 받은 명함 = 고객으로 들이는 입구
- 1차 행동 [고객으로 추가] / [기존 고객의 담당자로]. 들이는 화면은 Q sale `ClientAddDrawer` prefill 확장(새 폼 금지).
- `saved_name_cards`(받은 명함 탭)는 남긴다 — 공개 페이지 [보관] 은 워크스페이스 문맥이 없는 곳에서 눌리므로 계정 단위 «받는 자리» 가 필요. 탭 설명 한 줄 추가. 고객 행은 값 복사(스냅샷).
- 같은 워크스페이스 멤버의 명함엔 [고객으로] 없음(«멤버가 이긴다»). 공개 페이지에서 바로 고객 생성 금지. 자동 저장 금지.

### 결정 2 — 고객 담당자: `client_contacts` 표(고객 아래 추가 담당자 주소록) + clients 칸 2
- clients 에 `job_title`·`department` 만. 대표 담당자 사본(미러)은 만들지 않는다.
- `client_contacts`: id · business_id · client_id(CASCADE) · name · name_en · job_title · department · email · mobile · phone · fax · address · memo(500) · photo_file_id · source ENUM(manual,name_card,photo,mail,chat) · source_card_id · created_by · sort_order · 시각. 인덱스 (business_id,email)·(client_id). 고객당 50.
- 불변식: ① 담당자는 허브가 아니다(contact_id 를 갖는 다른 표 없음) ② 담당자는 로그인하지 않는다(초대·계정·한도·accessKindOf 는 clients 한 행) ③ 고객 한도에 안 센다.
- 맞추는 곳 한 함수씩: `mailLink.matchClientByAddresses` 3순위(billing 다음·alias 앞) — 같은 회사 두 번째 사람의 메일이 그 고객에 붙는다 · sale_save 메일 승격·명함 들이기 전에 같은 함수로 «이미 있는 고객 — 담당자로?» · saleMailCriteria·clientAccess·client_invites·promoteClientToMember 변경 없음 · billing/project 연락처·email_aliases 는 합치지 않음(«청구 담당자로 지정» 체크 = 복사까지).
- 대표/추가 분기 판정은 `services/clientContacts.js` 한 곳. 명함 사진은 File(`client_id`) — 쿼터·휴지통·EXIF 제거 그대로, 고객 행에 사진 칸 없음.
- 라우트 새 파일 `routes/sale_contacts.js`(saleCommon 권한 체인) · 감사 `client.contact_*` · 실시간 `client:updated` 신호 · 화면 `ClientRecordSections` 에 «담당자» 절. ESCO 는 담당자에 연결하지 않는다.

### 결정 3 — 명함 사진 읽기(한다, Irene 질문 없음)
