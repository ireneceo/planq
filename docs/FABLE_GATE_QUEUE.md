## 1. Q Note 회의록을 Cue 범위로 (2026-09-08, commit `f584036f`)

**판정: R=1** — 개인 자료(회의록)가 LLM 프롬프트로 들어가고, Cue 답변에는 **고객 대화방으로
나가는 경로**(`cue_orchestrator`)가 따로 있다. 문이 잘못 열리면 되돌릴 수 없다.
**S=1** — 새 절단면(어느 경로에서 개인 자료를 허용할 것인가)을 요구사항에서 자동으로 못 뽑는다.

### 무엇을 만들었나
- `q-note/routers/sessions.py` → `GET /api/sessions/internal/search`
  (x-internal-api-key, `business_id` + **`user_id` 강제** — 이 조건이 사적 공간 정책의 집행 지점)
- `dev-backend/services/qnoteContext.js` → 통로 하나. 2.5s 타임아웃, 실패해도 `[]`
- `dev-backend/services/cue_context.js` → `personalScope` 인자 신설(기본 `'none'` = fail-closed).
  `personalScope === 'self' && internal && userId` **셋 다** 맞을 때만 싣는다
- `dev-backend/routes/cue.js` `/help` 만 `personalScope: 'self'` 를 넘긴다.
  `cue_orchestrator` 는 넘기지 않는다(= 대화방 경로는 구조적으로 못 탄다)
- 커버리지 문구도 같이 고쳤다 — 실었을 때만 "조회함", 안 실었으면 "**본인 노트뿐**" 이라고 말한다

### 왜 `audience === 'internal'` 로 갈음하지 않았나
그 값의 뜻은 "스태프 전용 정보 허용" 이지 "받는 사람이 묻는 사람 하나" 가 아니다.
지금은 우연히 같지만, 내부 **공유** 대화방용 경로가 나중에 `internal` 로 들어오면
남의 눈에 내 회의록이 조용히 실린다. 뜻이 다른 두 가지는 값도 나눴다.

### 자체 검증 (Fable 미검증)
`node scripts/e2e/run.js --suite qnotecue` — 7/7, 그중 **5개가 음성 대조군**:
① 본인 노트는 요약 본문 낱말로 뜬다
② 같은 워크스페이스 **owner** 여도 남의 노트는 안 뜬다
③ `personalScope` 기본값이면 안 뜬다 (= 대화방 경로 보호)
④ `audience='client_facing'` 이면 `personalScope='self'` 여도 안 뜬다
⑤ 다른 워크스페이스에서는 안 뜬다
⑥ 내부 엔드포인트 — 키 틀리면 401 · `user_id` 가 다르면 0건
⑦ 커버리지 문구가 거짓말하지 않는다
가드를 깨뜨려 반증도 했다(문을 넓히면 ③④⑦이 빨강으로 뒤집힌다).

### Fable 에게 물을 것
1. `personalScope` 문이 **정말로** 답이 묻는 사람에게만 가는 경로와 1:1 인가.
   `/api/cue/help` 응답이 다른 곳으로 재사용되는 경로가 있는가(MCP 읽기 서버·Cue tools 포함).
2. 프롬프트 주입 표면 — 회의록 발췌(3건 × 700자)를 `<<<회의록: …>>>` 구분자로 가뒀는데,
   전사에 그 구분자 문자열이 그대로 들어 있으면 탈출 가능한가.
3. q-note `/internal/search` 의 LIKE 조합(필드 6 × 낱말 10)이 SQLite 에서 감당 가능한가.
   `INTERNAL_API_KEY` 만으로 지키는 표면이 하나 더 늘어난 것의 위험.
4. 개인 노트(L1)를 포함시킨 판단이 옳은가 — `/internal/by-entity` 는 L1 을 **뺀다**
   (그건 남에게 보이는 히스토리라서). 여기는 본인에게만 가므로 포함했다. 이 비대칭이 맞는가.

## 2. 채팅 민감정보 보호 (#407) — **설계만, 아직 구현 안 함** (2026-09-08)

Irene(#407): *"채팅에서 비번과 같은 중요내용 보내면 어떻게 보안처리 해?
절대 공유되서 문제되는 일 없게 개발된 거 맞아? 확인하고 말해줘."*

**판정: R=1** — 멀티테넌트 격리·암호화·LLM 반출 축을 동시에 건드린다. 틀리면 되돌릴 수 없다.
**S=1** — "어디까지가 보호인가" 가 요구사항에서 자동으로 안 나온다(편의↔보안이 정면으로 충돌).

### 코드로 확인한 현재 상태 (2026-09-08)
| 축 | 사실 |
|---|---|
| 전송 | HTTPS + helmet ✅ |
| 저장 | `messages.content` **평문 TEXT**. 앱 레벨 암호화 없음. (`services/encryption.js` 는 있고 클라우드 토큰·메일 비밀번호에만 쓰인다) |
| 읽는 사람 | `access_scope.canAccessConversation` — **`isMemberOrAbove` 면 무조건 true**. 즉 워크스페이스 멤버는 그 워크스페이스 어느 대화방이든 읽는다. 고객(Client)만 참여 방으로 제한 |
| LLM | `cue_context.getConversationHistory` 가 최근 대화를 프롬프트에 싣는다 → 채팅에 쓴 비밀번호가 외부 모델로 나간다 |
| 백업 | DB 덤프에 평문 |
| 삭제 | 화이트리스트 마스킹으로 새지 않는다 ✅ (원본은 정책상 DB 보존) |

**정직한 결론: 채팅은 비밀번호 보관용으로 설계돼 있지 않다.** 이미 맞는 자리가 있다 —
Q info 의 **secret 타입 항목**(값 가림 · 눌러야 보임 · CSV 내보내기 제외 · 검색 제외).

### 올릴 설계안 (셋을 따로 판정받는다)
1. **Cue 프롬프트 마스킹** (R=0·F=1 — 이것만은 자체 검증 가능)
   대화 히스토리를 프롬프트에 싣기 전에 비밀번호꼴 문자열을 가린다.
   ★ 함정: 무엇이 "비밀번호꼴" 인가를 정규식으로 정하면 반드시 오탐/미탐이 난다.
     오탐은 답변 품질만 깎지만 **미탐은 유출**이다 — 그래서 넓게 잡고, 가린 사실을 프롬프트에 밝힌다.
2. **대화방 접근을 참여자로 좁히기** (R=1)
   `isMemberOrAbove → true` 를 참여자·프로젝트 멤버로 좁히면 **지금 보이던 것이 안 보이게 된다** —
   운영 중인 워크스페이스의 기존 동작을 깨는 변경이라 Irene 결정과 이행 경로(기존 대화 처리)가 먼저다.
3. **메시지 본문 암호화 저장** (R=1)
   키 관리·검색(현재 LIKE 검색·FULLTEXT)·번역 캐시·Cue 색인이 전부 평문 전제다.
   암호화하면 그 기능들이 같이 죽는다 — **무엇을 포기할지**가 설계의 본체다.

### Fable 에게 물을 것
1. 1번 마스킹의 미탐 표면 — 어떤 형태가 새는가(멀티라인·base64·URL 안 자격증명·이미지 OCR 경로).
2. 2번을 적용할 때 **이미 나가 있는 것**(알림 링크·게스트 링크·검색 색인·Cue 답변 캐시)은 어떻게 되는가.
3. 3번을 하면 죽는 기능 목록이 정확히 무엇인가. 부분 암호화(민감 표시한 메시지만)가 성립하는가.
4. 그냥 **"채팅에 비밀번호를 쓰지 마세요" 를 화면이 말하는 것**(입력 시 경고 + Q info secret 로 유도)이
   1~3보다 나은 선택인가. 우리는 이쪽이 정답에 가깝다고 본다 — 반증해 달라.

## 3. 워크스페이스 격리의 **판정 축** — 활성인가 멤버인가 (2026-09-08, 결정 대기)

Irene: *"워크스페이스별로 완벽히 데이터 차단되는 거 너무 중요한데. 이거 보안문제 아니야?
플랫폼관리자 정보도 마찬가지고."*

**판정: R=1 · S=1** — 멀티테넌트 격리 축을 바꾸는 것이고, 바꾸면 이미 나가 있는 링크의
도달성이 달라진다(되돌리기 어렵다). 그리고 "무엇이 올바른 동작인가" 가 요구사항에서
자동으로 안 나온다 — 격리를 조이면 편의가 깎이는 정면 상충이다.

### 지금 상태 (2026-09-08 실측 — 추정 아님)
```
active = B(6) 인 계정으로 실호출
  200  /api/tasks/2178/detail      B 업무 (활성 워크스페이스)
  200  /api/tasks/2177/detail      A 업무 — 내가 A 멤버라서 열린다 (활성이 아닌데도)
  200  /api/tasks/by-business/5    A 목록도 같음
  403  /api/tasks/by-business/1    멤버가 아닌 워크스페이스 → 여기서 막힌다
  403  /api/admin/overview         비관리자 → insufficient_role
  403  /api/admin/users            비관리자 → insufficient_role
```
`--suite tenant` 9/9 · `--suite l1` 4/4 — **테넌트 경계(비멤버) 자체는 뚫려 있지 않다.**
서버 판정 축이 "지금 보고 있는 워크스페이스" 가 아니라 **"이 사람이 그 워크스페이스의 멤버인가"**
(`middleware/access_scope.js` `getUserScope(userId, businessId, ...)` — businessId 는 요청이 준다).

### 그래서 무엇이 문제인가
탭·링크가 섞이면 **화면이 그대로 섞인다.** 남에게 새는 것이 아니라, 내가 B 를 보고 있다고
믿는 화면에 A 의 것이 올라온다 — 잘못된 고객·잘못된 청구에 붙일 수 있는 종류의 위험이다.
(입구 두 개는 2026-09-08 에 막았다: `7bc70ef7` 기록 시점 범위 결정 · `5446a277` 저장된 오염 청소.
 하지만 그것은 **탭**이라는 한 입구다. 알림 링크·공유 링크·주소 직접 입력은 그대로 남아 있다.)

### Fable 에게 물을 것
1. 축을 "활성 워크스페이스" 로 바꾸는 것이 옳은가. 바꾸면 **다른 워크스페이스의 알림·공유 링크**가
   전환 없이는 안 열린다 — 그 동선을 어떻게 설계해야 사용자가 막다른 골목을 안 만나는가
   (링크에 workspace 힌트를 실어 자동 전환? 그러면 전환이 조용히 일어나는 것도 위험한가).
2. 부분 적용이 성립하는가 — 목록·검색·집계는 활성 축으로 좁히고, **id 로 직접 지목한 상세**만
   멤버 축을 허용하는 안. 그러면 "목록엔 없는데 링크로는 열린다" 가 되는데 그게 더 나쁜가.
   (memory `feedback_list_blocked_search_open` — 진입점마다 술어가 갈라지는 계열)
3. 지금 축을 유지한다면, **화면이 어느 워크스페이스의 것인지 항상 말하게** 하는 것으로 충분한가.
   충분하다면 그 표시가 반드시 있어야 할 표면 목록을 달라(상세·드로어·팝아웃·알림·인쇄·내보내기).
4. 플랫폼 관리자 축: `requireRole('platform_admin')` 하나로 충분한가. 관리자 화면이 워크스페이스
   맥락과 섞여 뜰 수 있는 경로(탭·팝아웃·딥링크)가 더 있는가.
5. `active_business_id` 는 **DB 에 저장되는 사용자 상태**다(다중 기기·다중 탭에서 한 벌).
   데스크탑에서 A 를 보는 동안 폰에서 B 로 바꾸면 데스크탑의 다음 요청은 어느 축인가 —
   이 경합이 위 1·2번 설계에서 어떻게 되는가.

### 올리기 전 준비물 (이미 있음)
- 실측 스크립트: 임시 다중소속 계정 → A/B/비멤버/관리자 4축 실호출 (이 대화의 xws 프로브)

### Fable 에게 물을 것
1. **결제 축(leave_type)과 종류 축(category)을 나눈 것이 옳은가.** "무급 병가" 가 표현 가능해야
   한다고 봤는데, 두 축이 곱해지면서 잔여 계산에 빠진 조합이 있는가.
2. `getBalance` 의 **최상위 값이 전 종류 합**인 것 — 옛 호출부(근태 화면·통계)가 그 합을
   "연차 잔여" 로 읽고 있는 곳이 있는가. 있다면 조용히 틀린 숫자를 보여준다.
3. 승인 검사를 종류별로 바꾸면서, **이미 pending 인 옛 신청**(category='annual' 로 백필됨)이
   승인될 때 잘못된 통에서 깎이는 경로가 있는가.
4. ENUM append 가 아니라 **신규 컬럼**이라 무중단이었다고 판단했다. 운영 데이터에서 맞는가.
5. 종류를 나중에 **워크스페이스별 커스텀**으로 넓힐 때 이 ENUM 이 막다른 길인가.
