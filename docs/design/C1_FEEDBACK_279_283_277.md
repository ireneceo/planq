## 1. #279 — 기간 편집 권한

### 1.1 지금 상태 (실측)

`dev-backend/routes/tasks.js:1016-1017`
```js
due_date:   () => isCreator || isOwnerOrAdmin,
start_date: () => isCreator || isOwnerOrAdmin,
```
요청받은 업무 = **내가 담당자 · 남이 작성자** → `403 forbidden_fields:due_date`.

프론트 `TaskDetailDrawer.tsx:1312` · `QTaskPage.tsx:2071` 의 `DateRangeCell` 에는
**권한 플래그가 아예 없다**(`canEditTitle`/`canEditBody`/`canEditRecurrence` 는 있는데 날짜만 없음).
→ 담당자에게 편집 가능한 UI 를 보여주고 **저장 시점에만 실패**시킨다.

### 1.2 규칙이 서로 어긋나 있다 (이게 진짜 병인)

- `CLAUDE.md` 운영 정책: **"할일 마감 지연: 빨간 뱃지, 마감 연장은 담당자 이상"**
- `PERMISSION_MATRIX §5.7` / 코드: `due/start → 작성자 OR owner OR admin` (담당자 제외)

**둘 중 하나는 거짓말이다.** 신고자는 문서 쪽(담당자 가능)을 기대하고 조작했다.

### 1.3 결정 (설계안)

**담당자를 기간 편집 주체에 포함한다.** 근거:
- 착수일(`start_date`)은 수행자 영역이다 — 언제 시작할지는 담당자가 정한다.
- 마감일(`due_date`)은 운영 정책이 이미 "담당자 이상 연장 가능" 으로 선언돼 있다.
- 담당자가 못 바꾸면 "요청받은 일의 일정을 스스로 못 잡는" 상태가 되어 Q Task 의 전제(담당자가 마감 책임)와 모순된다.

```js
due_date:   () => isAssignee || isCreator || isOwnerOrAdmin,
start_date: () => isAssignee || isCreator || isOwnerOrAdmin,
```

**단, 발주자 보호장치를 같이 넣는다** (권한만 열고 끝내면 "내가 준 마감이 조용히 밀린다"):
- `due_date` 가 **담당자에 의해** 변경되면 `TaskStatusHistory` 와 동급의 이력이 남고,
  **요청자에게 알림**(`notify`)이 간다 — "담당자가 마감일을 8/20 → 8/25 로 변경했습니다".
- 작성자·owner 가 바꿀 때는 담당자에게 간다 (기존 알림 축과 동일 방향).

`recurrence_rule` 은 **열지 않는다** — 반복 정의는 의뢰 명세(발주자 영역)다. `due_date` 가 필요한
파생 규칙이라 담당자가 마감을 바꿔도 반복 규칙 자체는 발주자 소유로 남는다.

### 1.4 프론트 가드 (누락분 보완)

`canEditDates = iAmCreator || iAmAssignee || iAmWsOwner` 를 신설하고
- `TaskDetailDrawer` 기간 셀 · `QTaskPage` 리스트 기간 셀 둘 다 `disabled` + `읽기 전용` 힌트
- 권한 없으면 애초에 피커가 안 열린다 (실패 토스트를 보여주는 대신 **열지 않는다**)

### 1.5 두 번의 PUT 경쟁 (덤으로 잡히는 결함)

`onSave={(s,d)=>{ saveField('start_date',s); saveField('due_date',d); }}` — **동시 PUT 2발**.
하나가 403 이면 **절반만 저장**되고, 둘 다 성공해도 마지막 응답이 이전 값을 덮을 수 있다.
→ **단일 PUT 으로 합친다**: `saveFields({ start_date: s, due_date: d })`.
(백엔드 PUT 은 이미 여러 필드를 한 번에 받는다 — 라우트 변경 불필요.)

## 5. #277 — 표시명 정본 이원화 (가장 넓은 결함)

### 5.1 실측 데이터 (운영)

```
users#3        name='한수정'  name_localized=NULL
business_members(biz1,user3)  name='루아'  name_localized={"en":"Lua"}
```
신고된 4개 업무는 **전부 business_id=1 · assignee_id=3** 인데 한 행만 '한수정' 으로 나왔다.

### 5.2 규약이 두 벌이다

| 층 | 쓰는 필드 | 파일 |
|---|---|---|
| 백엔드 `applyMemberDisplayName` | `obj.name` / `obj.name_localized` **덮어쓰기** | `services/displayName.js:56-57` |
| 백엔드 `/businesses/:id/members` | `user.display_name` / `user.display_name_localized` **추가** | `routes/businesses.js:818` |
| 프론트 `displayName()` | `display_name_localized` > `display_name` > `name_localized` > `name` | `utils/displayName.ts:21` |

→ **같은 사람의 표시명이 경로마다 다른 필드에 실린다.** 어느 한 경로라도 헬퍼를 안 태우면
계정명이 그대로 새어나온다. 이것이 "어떤 건 맞고 어떤 건 틀린" 의 구조적 원인이다.

### 5.3 ★ 진짜 병인 (Fable 게이트 치명-1 으로 정정)

**초판 서술은 틀렸다.** "소켓 payload 에 assignee 가 아예 없다" 는 사실이 아니다 —
주 생성 경로 `services/actions/task_actions.js:430-447`(`afterCreate`)는 이미
`assignee`/`requester` 를 include 하고 `applyMemberDisplayName` 까지 태운다.

**실제로 새는 곳은 AI 예측 broadcast 다.**

`services/actions/task_actions.js:517-531`
```js
const updated = await Task.findByPk(taskId, {
  include: [ ..., { model: User, as: 'assignee', ... }, { model: User, as: 'requester', ... } ],
});
const payload = { ...updated.toJSON(), latest_estimation_source: 'ai', ... };
io.to(`business:${businessId}`).emit('task:updated', payload);
//  ↑ applyMemberDisplayName 을 **안 태운다**
```
프론트는 `setAllTasks(prev => prev.map(t => t.id===task.id ? { ...t, ...task } : t))`
(`QTaskPage.tsx:699`) — **spread 라 정상 표시명('루아')이 계정명('한수정')으로 덮어써진다.**

업무 생성 시 `autoAiEstimate: true`(`routes/tasks.js:440-447`)로 백그라운드 추정이 돌기 때문에,
**페이지를 열어둔 채 추정 broadcast 를 받은 행만** 계정명으로 플립된다 →
"같은 워크스페이스·같은 담당자 4건 중 1건만 한수정" 증상과 정확히 일치.

**따라서 `serializeTaskForBroadcast` 적용 대상에 `task_actions.js:531` 을 반드시 포함한다.**

### 5.3b raw `toJSON()` emit 지점 — 5곳이 아니라 최소 7곳

`routes/tasks.js:1135-1136` · `routes/tasks.js:419-422`(PATCH `/:id/time`) ·
`routes/tasks.js:1356-1360`(copy → `task:new`) · `services/taskTransition.js:25` ·
`routes/task_priority.js:27-28` · `routes/focus.js:96-97` · `routes/task_tags.js:266`
→ 전부 헬퍼 경유로 일원화한다.

### 5.4 설계

**(a) 정본을 `display_name*` 한 벌로 모은다.**
`applyMemberDisplayName` 이 `name`/`name_localized` 를 덮어쓰는 **동시에**
`display_name`/`display_name_localized` 도 채운다. 프론트 헬퍼가 이미 이 필드를 최우선으로
읽으므로, 이후 어느 경로를 타든 워크스페이스 표시명이 이긴다.

> 기존 `name` 덮어쓰기는 **유지**한다 — 제거하면 `user.name` 을 직접 읽는 화면이 전부 회귀한다.
> (그런 화면을 전수로 `displayName()` 로 바꾸는 것은 이 청크의 범위를 넘는다. 정본을 심어두고
> 다음 청크에서 raw `.name` 사용처를 줄인다.)

**(b) 소켓 task payload 에 사람 정보를 싣는다.**
`serializeTaskForBroadcast(task)` 공용 헬퍼 1벌을 만들어 `assignee`/`requester` 를 포함하고
`applyMemberDisplayName` 을 통과시킨다. 위 5개 emit 지점이 전부 이 헬퍼를 쓴다.
(메모 `feedback_dual_column_authority_write_side` — 쓰기측 전 경로를 같이 고친다.)

**(c) 프론트 낙관적 갱신도 같은 규약으로.**
`QTaskPage.tsx:1958` · `TaskDetailDrawer.tsx:1294` 가 `{ id, name }` 만 만들어 넣는다.
`{ id, name, display_name, display_name_localized }` 로 채워 서버 응답과 모양을 맞춘다.

## 5.5 Fable 설계 게이트 반영 (APPROVED_WITH_CHANGES)

**치명**
1. #277 진짜 병인 정정 → §5.3 반영 완료
2. **기간 편집 진입점 2곳 추가** — `pages/QProject/ProjectTaskList.tsx:516`(동일 DateRangeCell + 동일 이중 PUT `:270-273` + 가드 전무), `pages/QTask/QTaskPage.tsx:1288-1290` `extendDue`(지연 마감 빠른 칩, due 단독 PUT). emit 지점은 7곳 → §5.3b
3. **Q Note 선택은 path param** — `QNotePage.tsx:198` `useParams<{sessionId}>()`, 라우트 `/notes/:sessionId`.
   `URLSearchParams.has('session')` 술어는 **항상 false** 라 동작하지 않는다. 그리고 초기 상태
   `QNotePage.tsx:284-287` 이 `innerWidth < 900` 으로 무조건 접는다 — **breakpoint 도 1024 와 어긋난다**.
   → 초기값·핸들러 **둘 다** 수정 + 900→1024 통일

**중요**
1. `isAssignee` 개방은 **외부 파트너(client) 담당자에게도** 열린다 (PUT 은 `assertBusinessAccess` 라 client 통과). title/status 가 이미 같은 구조라 신규 구멍은 아니나 **명시 + 검증 케이스 추가**
2. `serializeTaskForBroadcast` 는 **배치 API** — `task_priority.js` 는 reindex 1회에 N건 emit. per-task 조회면 드래그 1번에 쿼리 폭증. `applyMemberDisplayName` 의 배열 배치를 그대로 쓴다
3. 헬퍼는 **부가 필드를 보존**해야 한다 — `reviewer_user_ids` · `actor_user_id` · `latest_estimation_source` · `ai_estimate`. 헬퍼가 base 를 반환하고 caller 가 extras 를 spread
4. **due 변경 이력은 이미 있다** — `routes/tasks.js:1088-1090` `event_type:'due_change'`. 이중 기록 금지, **신규는 알림만**
