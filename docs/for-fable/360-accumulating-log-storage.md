## 코드로 확인된 현재 구조 (사실만)

| | 저장소 | 화면 | 성격 |
|---|---|---|---|
| **Q info** | `kb_documents` | `/info` (KnowledgePage) | 정보 1건 = 항목 여러 개. 행 누적 아님 |
| **문서 안의 표** | `q_records` + `q_record_rows` | Q docs 문서(post `kind='table'`) 안에 임베드 | 행 누적 됨. `posts.q_record_id` 로 연결 |

- 둘은 **다른 저장소·다른 화면**이다. `KnowledgePage` 는 `q_records` 를 한 번도 참조하지 않는다(실측 0건).
- `q_records` 는 이미 문서와 독립적일 수 있는 스키마다 — `project_id` nullable(NULL=워크스페이스 전역),
  사용자 정의 `columns` JSON, `read_policy`, `vlevel`, `target_member_ids`.
  **독립 자산으로 만드는 데 스키마 변경이 필요 없을 가능성이 높다** (검증 필요).
- 옛 `Q record` 메뉴는 폐지됨(`/records` → `/docs`). 남아 있던 이름은 2026-09-01 에 정리했다
  (라벨·i18n 네임스페이스 `qrecord`→`qtable`·주석). **기능 변경 아님, 이름만.**

## 이미 처리된 것 (설계와 무관하게 명백했던 것)

수정안 ② 중 "도달 진입로" 는 부분 처리했다 — 커밋 `a927ab94`.
`POST /api/records` 가 post 없이 표만 만들 수 있어 **운영에 도달 불가 표가 있었다**
(#12 "앱 스토어 개발자 계정", 행 15건, D-U-N-S·Team ID 포함). 생성 시 post 를 같이 만들고,
기존 고아는 백필(`scripts/backfill-orphan-record-posts.js`, 배포 체인 연결)한다.
가시성은 원본 표의 `vlevel`/`target_member_ids` 를 그대로 옮긴다(넓히지 않음, 실 API 6/6 검증).

## Fable 이 판단해야 할 것

1. **어느 그릇인가** — 표를 독립 자산으로 되살릴지(옛 메뉴 부활), Q info 에 "표 타입 정보" 를 넣을지,
   아니면 제3의 그릇인지. Irene 은 "레코드는 인포로 바꾼 것" 이라고 인식하고 있는데
   코드상 둘은 별개다 — **이 인식 차이 자체가 설계 입력이다.**
2. **문서 종속을 끊을 때의 절단면** — `posts.q_record_id` 를 통한 진입/권한/검색/휴지통이
   전부 post 에 붙어 있다. 표를 독립시키면 그 다섯을 어디에 다시 붙일 것인가.
3. **#354 와의 순서** — 수정안 ③(정기업무 산출물 저장 위치)은 #354 의 deliverable 필드와 한 몸이다.
   어느 것을 먼저 박아야 다른 하나가 자연히 풀리는가.
4. **250행 규모** — 연 250행 × 3 종류. 현재 표 UI(PostTableGrid)와 records 라우트 pagination 이
   그 규모에서 견디는가.
