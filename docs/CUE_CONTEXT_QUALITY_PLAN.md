# Cue 대화 품질 — 맥락 이해와 정보 파악 범위 (2026-09-19 착수 대기)

> Irene 2026-09-19: *"Cue 대화수준이 너무 낮아서 곤란해."* ·
> *"대화 맥락을 이해하는 수준이 너무 저급하고 워크스페이스에 대한 정보파악 범위가 너무 좁아.
> 위 내용 전반적으로 보완하고 나중에 fable에게도 한번 더 검토 시켜서 추가 보완 2차 해줘."*

**상태: 착수 전.** 아래는 실제 대화 1건을 코드·운영 데이터로 파악한 결과와 수리 계획이다.
**다음 세션에서 이 문서부터 연다.**

## 1. 무엇이 일어났나 (실측)

신고된 대화(요약): Irene 이 ①*"업무지연이 많은 직원은 누구야?"* 를 묻고 ②그걸 **개발요청으로
어떻게 정리하면 좋을지** 물었는데, Cue 는 ①에 답하지 못했고 ②에서는 **전혀 다른 주제(퍼플히어 POS
회의록)** 로 빠졌다. 같은 질문을 두 번 반복해도 같은 답이 돌아왔다.

### 근거 1 — 퍼플히어가 끌려온 이유는 **단어 하나**다
질문: *"개발요청을 하려는데 이걸 **어떻게** 정리해서 요청하면 될지 물었잖아"*
`cue_context.queryTerms()` 가 쪼갠 검색어:
`개발요청을 · 개발요청 · 하려는데 · 이걸 · 어떻게 · 정리해서 · 요청하면 · 될지 · 물었잖아`

`likeAny()` 는 이 단어들의 **OR + `LIKE %term%`** 이고 **관련성 순위가 없다.**
운영 q-note 실측 — 퍼플히어 노트 2건 중:
| 노트 | 길이 | 걸린 검색어 |
|---|---|---|
| #2 퍼플히어 수정필요 | 651자 | **없음** |
| #9 퍼플히어 | 2,904자 | **`어떻게` 하나** |

→ 2,904자 회의록이 일상어 한 단어로 «관련 자료» 가 되어 프롬프트에 실렸고, 모델은 들어온 자료를
  쓰려고 했다. Cue 의 사후 설명(*"검색 결과에 있어서 같이 보여준 거고요"*)은 **사실이 맞다** —
  다만 그게 왜 잘못인지를 모른다.

### 근거 2 — 「누가 지연이 많은가」는 **구조적으로 답할 수 없다**
- `services/cue_tools.js` 의 도구는 **6개이고 전부 쓰기**:
  `create_task` · `create_event` · `create_document_draft` · `submit_review` · `complete_task` ·
  `add_task_comment`. **조회·집계 도구가 0개.**
- `cue_context.getWorkspaceOverview()` 가 업무에 대해 주는 것은 두 가지뿐:
  - `ov.overdue` — 워크스페이스 **전체 지연 건수 하나**(담당자 축 없음)
  - `ov.urgentTasks` — 마감 임박순 **limit 10**
- Cue 의 답 *"임박·지난 업무 10건 중 담당자가 명시된 건 전부 irene"* 은 **그 10줄을 그대로 읽은 것**이고,
  거기서 *"irene 쪽에 몰려 있다"* 로 **넘겨짚었다.** 10건 표본으로 사람을 평가하는 결론은 위험하다.

### 근거 3 — 메타 질문인데도 워크스페이스를 뒤진다
*"이걸 어떻게 정리해서 요청하면 좋을까"* 는 **워크스페이스 데이터가 필요 없는 질문**이다.
파이프라인은 질문 종류를 가리지 않고 **항상** 검색한다 → 상관없는 자료가 들어오고 답이 그쪽으로 끌린다.

### 근거 4 — 맥락 유실은 «이력 부족» 이 아니다
`HISTORY_TURN_LIMIT = 10` 으로 이력은 넘어간다. 문제는 **검색 결과 덩어리가 프롬프트를 지배**해
「무엇을 묻는지」가 묻힌 것이다. 같은 질문을 두 번 해도 같은 자료가 들어오니 같은 답이 나온다.

## 2. 수리 계획 (우선순위)

| 순위 | 무엇 | 왜 · 판정 |
|:--:|---|---|
| **1** | **검색에 관련성 기준을 건다** — ①일상어 불용어 제외(어떻게·정리·요청·확인·필요·하려는데…) ②**한 단어만 걸린 것은 버린다**(최소 2개 일치 또는 가중치 합 기준) ③제목 일치 가중 ④점수순 상한 | 지금은 «어떻게» 한 단어로 2,904자가 딸려온다. **모든 대화에서 일어난다** — 체감 품질 저하의 가장 큰 몫. R=0·S=0·F=1(질문 표본으로 «걸린 자료» 를 세면 참/거짓이 갈린다) |
| **2** | **조회 도구를 준다** — 담당자별 지연·부하 집계 등 **읽기 도구**. 지금은 쓰기 6개뿐 | «누가 지연이 많나» 류는 도구 없이 영영 못 답한다. ★ **지표를 Irene 이 정해야 한다** — 지연 건수 / 지연 비율 / 평균 지연 일수 / 기간 |
| **3** | **표본으로 단정하지 않게** — 잘린 목록만 본 상태면 «10건 기준» 임을 말하게(프롬프트 계약) | 사람 평가에 표본 추정은 위험하다. 지금은 그 사실을 숨기고 단정했다 |
| **4** | **메타 질문은 검색을 건너뛴다** — "어떻게 쓰면 좋을까" 류 | 없는 맥락을 끌어와 엉뚱한 답을 만든다 |
| **5** | **정보 파악 범위 확대** — Cue 가 못 보는 영역(개인 캘린더·고객 활동 이력 등) 중 **무엇을 열지** 정리. 권한 축(`access_scope`)과 같이 본다 | Irene 의 «정보파악 범위가 너무 좁아» 는 여기다. **R=1 영역이 섞인다**(권한·격리) — 열 범위를 정하는 것은 Fable 판단이 필요하다 |

### 하지 말 것
- 검색을 끄거나 상한만 줄이는 것 — 그러면 정작 필요한 자료도 사라진다. **순위를 만들어야 한다.**
- 도구를 늘리면서 권한 검사를 건너뛰는 것 — 조회 도구도 `access_scope`·`business_id` 를 탄다.

## 3. Fable 2차 검토 (Irene 지시)
1차 보완을 끝낸 뒤 **Fable 에게 다시 검토시켜 2차 보완**한다. Fable 에게 물을 것:
- 관련성 기준이 **놓치는 쪽**(있어야 할 자료가 안 걸리는 경우)을 실제 질문 표본으로 재 달라 —
  나는 «덜 걸리게» 만들 수는 있어도 «맞게 걸리는지» 를 혼자 가르기 어렵다.
- 조회 도구가 열 **데이터 범위와 권한 축** — 멤버별 지연 통계는 **인사 정보**에 가깝다.
  누가 볼 수 있어야 하는가(owner/admin만? 본인 것만?)는 R=1 판단이다.
- 정보 파악 범위 확대(5번)에서 **열면 안 되는 것**.
