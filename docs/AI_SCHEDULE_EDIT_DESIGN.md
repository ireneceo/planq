# AI 일정 수정 — 설계

> Irene 2026-09-10: *"전체 프로젝트 일정을 늘린다거나 마감기간 당기고 업무들 기간들 줄인다거나
> 담당자 다 바꾼다거나 어느 단계까지 다 완료처리 한다거나 중간에 어떤 업무그룹을 넣고 배치를 바꾸게
> 한다거나 하는 [AI로 지금일정 수정하기] 이런 기능은 있을 수 없을까? 전체적으로 잡고 싶거나
> 변경해야 할 때 엄두가 안나. 특히 기간들."*

**상태 (2026-09-11): 서버 1차(이동·목표 마감 압축) 구현 · Fable PASS · 화면(`ScheduleEditModal`) 미착수 · 미배포.**
적용·되돌리기는 **업무별로 지금 값을 대조**한다 — 미리보기 뒤 누가 바꾼 업무는 덮지 않고 건너뛴다(§5.2 결과 기록).

---

## 0. 왜 지금 엄두가 안 나는가 — 코드로 확인한 사실

| 확인한 것 | 결과 |
|---|---|
| 여러 건을 한 번에 옮기는 도구가 있는가 | **없다.** `services/cue_tools.js` 의 도구 6개(`create_task`·`create_event`·`create_document_draft`·`submit_review`·`complete_task`·`add_task_comment`)가 **전부 한 건씩** 처리한다 |
| 행동 계층은 있는가 | **있다.** `services/actions/task_actions.js` — 머리말이 "사람도 Cue 도 외부 에이전트도 **같은 문**을 지난다" 고 못박고 있고, 이 문을 지나야 이력(`TaskStatusHistory`)·알림·소켓 broadcast·Focus 정리가 자동으로 붙는다 |
| 그 계층이 **날짜·담당자 수정**을 제공하는가 | **아니다.** `updateTask` 계열이 **0건**. 생성(`createTask`)과 상태 전이(`ack`·`submitReview`·`complete`·`hold` 등)만 있고, 날짜·담당자·그룹은 `routes/tasks.js:1160` PUT 이 **직접 쓴다** |
| 단계 개념이 있는가 | **있다.** `project_stages` + `services/projectStageEngine.js` (멱등 재계산) |
| 그룹 개념이 있는가 | **있다.** `project_workstreams` (= 업무 그룹) |

**결론:** 배관은 깔려 있고 **없는 것은 두 가지**다 —
① 행동 계층의 **필드 수정 액션**, ② 그것을 여러 건에 거는 **묶음 도구**.

이것이 "엄두가 안 난다" 의 기술적 실체다. 지금은 업무를 하나씩 열어 날짜를 고치는 길밖에 없다.

## 1. 설계 원칙 — 무서움을 없애는 것이 먼저다

기간을 한 번에 바꾸는 것이 무서운 이유는 **되돌릴 수 없어서**다.
그래서 설계의 중심을 "AI 가 잘 고쳐준다" 가 아니라 **"보고 나서 누르고, 틀리면 한 번에 되돌린다"** 에 둔다.

1. **AI 는 제안만 한다. 쓰기는 사람의 클릭이다.**
   AI 는 `변경안(plan)` 을 만들고, 사람이 전후를 나란히 본 뒤 적용한다.
   (memory `project_agent_permission_model` — Cue 는 위임자 권한으로만 행동한다)
2. **적용은 행동 계층 한 문으로.**
   새 라우트에서 직접 `UPDATE` 하면 이력·알림·소켓이 그 경로에만 빠진다 — 이 저장소에서 이미 났던
   사고다(action layer 머리말: *"Cue 가 일을 끝내도 아무도 모르고 화면도 안 갱신됐다"*).
3. **묶음 되돌리기.** 한 번의 수정에 `batch_id` 를 달고, 되돌리기 한 번에 전부 원복.
   이것이 없으면 사용자는 못 쓴다.

## 2. 화면 (텍스트 와이어 — 코드 아님)

```
프로젝트 > 업무 탭 상단          [AI로 일정 수정하기]

┌ 무엇을 바꿀까요? ───────────────────────────────┐
│  "전체를 2주 뒤로"     "10/31 마감에 맞춰 줄여줘"      │
│  "디자인 단계까지 완료로"  "김OO 업무를 박OO에게"        │
└────────────────────────────────────────────┘
        ↓  AI 는 **쓰지 않는다. 변경안만 만든다**
┌ 이렇게 바꿉니다 (17건) ──────────────────────────┐
│  업무             지금          →   바뀜            │
│  와이어 초안    09/12~09/18   →  09/26~10/02       │
│  시안 A         09/19~09/25   →  10/03~10/09       │
│  …                                               │
│  ⚠ 3건은 주말·공휴일이라 하루 당겨집니다              │
│  ⚠ 2건은 이미 완료 — 건드리지 않습니다                │
│  ⚠ 1건은 담당자가 달라 시간 기록이 유지됩니다           │
│                                                  │
│         [취소]              [17건 적용]            │
└────────────────────────────────────────────┘
        ↓  적용 후 (스낵바 아님 — 목록 상단 줄)
   "17건 적용됨 · 되돌리기"      ← 한 번에 전부 원복
```

미리보기가 이 기능의 **본체**다. 여기서 전후를 보지 못하면 나머지는 의미가 없다.

## 3. 연산 — 네 가지면 "기간" 요구가 덮인다

| 연산 | 뜻 | 규칙 |
|---|---|---|
| **이동** | 전체를 N일 뒤/앞으로 | 시작·마감을 같은 폭으로. 기간 길이 보존 |
| **압축·확장** | 목표 마감에 맞춰 비례 조정 | 전체 스팬 대비 각 업무 스팬을 비율로. 최소 1일 보장 |
| **영업일 보정** | 주말·공휴일에 마감이 걸리면 | 앞 영업일로 당긴다(뒤로 밀지 않는다 — 마감은 당기는 쪽이 안전) |
| **순서 보존** | 단계·의존이 뒤집히지 않게 | 앞 업무의 마감 > 뒤 업무의 시작이 되면 그 지점에서 멈추고 **경고로 보고** (임의 재배치 금지) |

담당자 일괄 변경·단계 일괄 완료·그룹 삽입은 **같은 미리보기 틀**에 얹는다.

## 4. 봉쇄 — 건드리지 않는 것

- **청구·금액.** AI 의 재무 접근은 영구 봉쇄가 정책이다(memory `project_ai_native_strategy`).
  일정이 바뀌어도 청구서는 사람이 따로 정한다.
- **결과물(`body`).** 담당자만 쓴다. 일정 수정이 결과물을 건드릴 이유가 없다
  (memory `feedback_responsibility_line`).
- **완료·취소된 업무.** 기본 제외. 지난 일정을 소급해 바꾸면 실제 걸린 시간 기록이 거짓이 된다
  (memory `feedback_actual_hours_focus_only`).
  - 미리보기에서 `include_closed` 로 **명시적으로 포함한 경우에만** 적용한다(원장 `params.include_closed`).
  - 미리보기 뒤에 완료로 바뀐 업무는 건너뛴다(`closed_since_preview`) — 실패가 아니라 상태 변화다.
  - ★ **업무 하나를 사람이 직접 고칠 때(업무 상세 PUT)는 완료 업무의 날짜도 바꿀 수 있다** — 실수한 날짜를
    바로잡는 길이고 화면이 그렇게 열려 있다. 일괄 제외는 "권한" 이 아니라 **묶음의 기본 범위**다 (2026-09-11 확정).
- **실제 시간(`actual_hours`).** 절대 손대지 않는다. 근거는 포커스 타이머뿐이다.

## 5. 만들 것

### 5.1 행동 계층 — `services/actions/task_actions.js`
```
updateSchedule(actor, task, { start_date, due_date }, opts)
reassign(actor, task, { assignee_id }, opts)
moveGroup(actor, task, { workstream_id }, opts)
```
- 반환 계약은 기존과 같다: `{ ok: true, data } | { ok: false, code, http }`
- **기존 PUT 라우트도 이 액션을 부르게 바꾼다.** 안 그러면 술어가 두 벌이 되고, 한쪽만 이력을 남긴다
  (memory `feedback_comment_lies_predicate_drifts` — 주석으로 약속하지 말고 같은 함수를 부르게).

### 5.2 묶음 원장 — `schedule_batches` (신규 1테이블)
| 컬럼 | 뜻 |
|---|---|
| `id`, `business_id`, `project_id`, `created_by`, `created_at` | |
| `prompt` | 사용자가 입력한 말 |
| `plan` JSON | 변경안 전문(전·후) |
| `applied_at`, `reverted_at` | |
| `items` JSON | `[{task_id, field, before, after}]` — **되돌리기의 근거** |

되돌리기는 `items` 를 역으로 같은 액션에 태운다. 원장이 없으면 되돌릴 수 없다.

### 5.3 도구 — `services/cue_tools.js`
`plan_schedule_change`(읽기·제안) / `apply_schedule_change`(쓰기, batch_id 발급) /
`revert_schedule_batch`. **쓰기 도구는 사람의 승인 토큰 없이 호출되지 않는다.**

### 5.4 화면
`pages/QProject/ScheduleEditModal.tsx` — 입력 → 미리보기 표 → 적용.
표는 `StandardModal` + 기존 표 컴포넌트를 쓴다(bespoke 금지).

## 6. 검증 — 무엇을 봐야 통과인가

- **미리보기가 쓰지 않는가** — `plan` 호출 전후로 `tasks` 스냅샷이 완전히 같아야 한다.
- **되돌리기가 원복하는가** — 적용 전 스냅샷 = 되돌린 뒤 스냅샷(전 필드).
- **멀티테넌트** — 남의 워크스페이스 업무가 한 건도 안 섞인다. 양성/음성 대조군.
- **권한** — 프로젝트 멤버가 아니면 403. 담당자 아닌 사람이 `actual_hours` 를 못 건드린다.
- **완료 업무 제외**가 실제로 동작하는가(양성 대조군: 강제 포함 옵션을 켜면 포함되는가).
- **이력·알림** — 적용 후 `TaskStatusHistory`/알림이 실제로 생겼는가.
  (일정 변경은 담당자에게 알려야 한다 — memory `feedback_notify_watcher_not_only_actor`)
- **화면** — 미리보기 표가 폰에서도 읽히는가(가로 스크롤 컨테이너).

## 7. 범위 제안 — 무엇부터

**1차: 이동 + 목표 마감 압축.** 신고의 "특히 기간들" 이 여기고, 되돌리기 구조를 이 둘로 먼저 세워
두면 나머지는 도구만 얹으면 된다.

**2차:** 담당자 일괄 변경 · 단계 일괄 완료.
**3차:** 그룹 삽입 + 배치 변경(순서 재배열은 의존 판정이 얽혀 가장 어렵다).

## 8. R/S/F 판정

- **R=1** — 여러 업무의 날짜·담당자를 한 번에 바꾼다. 되돌리기를 만들더라도 알림은 이미 나간다.
- **S=1** — "무엇이 올바른 동작인가" 가 요구사항에서 자동으로 안 나온다(영업일·의존·완료 제외).

→ **Fable 게이트 대상.** 설계 단계부터 올린다.
