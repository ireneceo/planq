## 2단계 — 실제 배포

```bash
cd /opt/planq && ./scripts/deploy-planq.sh
```

스크립트 진행 단계 (~3-5분):

1. preflight (dev 헬스 + SSH 도달)
2. show_changes (변경 파일 목록 + 사용자 확인 1회)
3. backup (운영 backend/frontend-build/q-note → /opt/planq/backups/{TIMESTAMP})
4. sync_backend (rsync dev-backend → 운영, .env 보호)
5. sync_frontend (npm run build + rsync → 운영 frontend-build)
6. sync_qnote (rsync q-note → 운영, --skip-qnote 옵션 가능)
7. install_deps (운영서버 npm ci --production)
8. sync_database (운영서버 node sync-database.js)
9. restart_server (PM2 reload planq-prod-backend / planq-prod-qnote)
10. reload_nginx (운영서버 sudo systemctl reload nginx — sudo 없으면 skip + Irene 안내)
11. verify (https://planq.kr/api/health 200 + 27/27 헬스체크 항목)
12. update_record (이번 배포 timestamp + commit hash 기록)

**플래그**:
- `--auto` — 확인 프롬프트 생략 (검증된 재배포 / 핫픽스)
- `--dry-run` — 미리보기만
- `--skip-build` — 백엔드만 (긴급 hotfix)
- `--skip-qnote` — Q Note Python 서비스 제외

## 3-B단계 — 피드백 장부 닫기 · 개발 현황 발행 (배포 스크립트가 자동으로 한다)

**둘 다 `scripts/deploy-planq.sh` 안에서 자동 실행된다. 손으로 할 일이 없다.**
여기 절차를 손으로 적어 두었더니 스크립트와 갈라졌다 — 문서는 `#숫자` 를 긁으라고 했고
스크립트는 트레일러만 인정한다. 본문의 `#숫자` 를 긁으면 **근거로 인용한 업무 번호까지**
딸려 나와 고치지도 않은 신고가 done 이 된다(2026-08-21 실측 반증).

### 장부 닫기 — `close_feedback()`
커밋 메시지에 **명시적 트레일러**를 적어야 닫힌다. 인용은 자유롭게 하되, 닫으려면 의도적으로 적는다.

```
Feedback-Closes: 213, 220        ← 이 배포로 해결된 신고
Feedback-Keeps-Open: 378         ← 앞선 커밋이 닫으려 했으나 부분 해결이라 철회
```

- **답글이 없는 건은 닫지 않는다** — 닫힌 이유를 모르는 사용자에게는 무시당한 것과 같다.
- 옛 커밋의 잔여분은 `scripts/feedback-close-backlog.txt` 에 번호를 적으면 다음 배포에 실린다.

### 개발 현황 발행 — `publish_dev_status()`
플랫폼 관리자 > **개발 현황** 화면에 이번 배포가 남는다. 배포 전에 **`docs/dev-status/next.json`** 을 쓴다.

```bash
# 내용 검사 (커밋 전에도 된다)
cd /opt/planq/dev-backend && node scripts/publish-dev-status.js ../docs/dev-status/next.json --dry-run
```

- 섹션 11종: `working_on` `in_progress` `completed` `behavior_changes` `issues`
  `blocked_on_human` `migrations` `check_areas` `backlog` `tooling_health` `undeployed`
- **기계가 아는 값은 적지 않는다** — 커밋 범위·배포 시각·롤백 경로·닫은 신고·스키마 변경 여부는
  배포 스크립트가 `--meta` 로 주입한다. 사람이 또 적으면 반드시 갈라진다.
- `completed[].verified` 는 `fable_pass` | `opus_only` | `none` 셋뿐이다. 다른 값은 발행이 거부된다.
- 본문에 HTML 태그를 넣지 않는다 — 이 화면은 텍스트로만 렌더한다(관리자 화면 저장형 XSS 차단).

## 4단계 — 배포 후 옵션 (Irene 에게 확인)

### 버전 업

```
"버전 올릴까요? (현재: x.y.z → 다음 patch x.y.{z+1})"
```

- 올린다고 하면:
  - **릴리즈 노트 자동 발행** (2026-08-25 신설):
    1. `docs/release-notes/v{버전}.json` 작성 — 이번 배포에 들어간 **사용자에게 보이는 변경만**,
       항목마다 `ko`/`en` 짝을 채운다 (내부 리팩토링·의존성 업 제외)
    2. dev 확인: `cd dev-backend && node scripts/publish-release-note.js ../docs/release-notes/v{버전}.json`
       (미발행으로 생성 — 새소식·인사이트 메뉴에서 내용 검토 가능)
    3. 운영 발행: `scp` 로 json 을 운영에 올린 뒤
       `ssh …prod "cd /opt/planq/backend && node scripts/publish-release-note.js /tmp/v{버전}.json --publish"`
    4. 사용자는 앱 안 **새 소식 드로어**에서 본다 (인사이트 목록에는 섞이지 않는다 — 의도된 분리)
    5. 사용 방식이 바뀐 항목이 있으면 **공지 배너**도 며칠 (관리자 메뉴 > 공지 배너, ko/en 각각)
  - `dev-backend/package.json` version 패치 +1
  - `dev-frontend/package.json` version 동일하게 맞춤 (현재 0.0.0 → 1.0.x 로 통일)
  - `DEVELOPMENT_PLAN.md` 상단 "최종 업데이트" 줄에 v버전 기록
  - `.claude/session-state.md` 마지막 업데이트 + 배포 commit/timestamp 기록
  - 한/영 릴리즈노트 출력 (아래 형식)
- 안 올린다고 하면: 버전 유지, 릴리즈노트 생략

### 릴리즈노트 출력 형식

이번 배포에 포함된 변경사항을 `git log {이전 prod 배포 commit}..HEAD --oneline` 또는 `DEVELOPMENT_PLAN.md` 최근 사이클에서 수집해 한/영 둘 다 작성.

```
📢 PlanQ Update v{버전}
YYYY년 M월 D일

━━━━━━━━━━━━━━━━━━

1️⃣ [기능명]

[설명 한 줄]

2️⃣ [기능명]

[설명 한 줄]

━━━━━━━━━━━━━━━━━━

📢 PlanQ Update v{버전}
Month DD, YYYY

━━━━━━━━━━━━━━━━━━

1️⃣ [Feature Name]

[Description line]

━━━━━━━━━━━━━━━━━━
```

규칙:
- 한글 + 영문 둘 다 필수
- 이모지 넘버(1️⃣ 2️⃣ 3️⃣ 4️⃣)와 줄바꿈으로 구조화
- 구분선은 `━━━━━━━━━━━━━━━━━━`
- 사용자에게 보일 항목만 (내부 리팩토링/디펜던시 업 제외)
