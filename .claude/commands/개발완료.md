### 0단계: 자동 가드 3축 (가장 먼저, 셋 다 통과해야만 다음 단계 진행)

```bash

node /opt/planq/scripts/e2e/run.js --suite tenant
```

> ⚠️ **0-F단계: Fable 판정 확인** (공용 기준 `~/dev-server/FABLE.md` · PlanQ 예시는 CLAUDE.md «Fable 사용» 절. 출처: 2026-07-21 «게이트 필수» → 09-06 «조건부» → 10-08 공용 기준).
> 마지막 게이트 마커 이후 바뀐 것(미커밋 + 커밋)을 본다. **훅(fable-gate-stop.sh)과 같은 방식**으로 판정한다 — 두 곳이 갈라지면 게이트가 거짓말한다.
> ```bash
> REPO=/opt/planq
> source "$REPO/.claude/hooks/fable-gate-paths.sh"
> CHANGED=$(git -C "$REPO" status --porcelain -- "${GATE_PATHS[@]}")
> LAST=$(jq -r '.commit // empty' "$REPO/.claude/.fable-gate.json" 2>/dev/null)
> if [ -n "$LAST" ] && git -C "$REPO" cat-file -e "${LAST}^{commit}" 2>/dev/null; then
>   COMMITTED=$(git -C "$REPO" log --format=%H "${LAST}..HEAD" -- "${GATE_PATHS[@]}"); else COMMITTED=""; fi
> if [ -z "$CHANGED$COMMITTED" ]; then echo "✅ 마지막 판정 이후 소스 변경 없음"; else
>   FP=$(printf '%s\n%s' "$CHANGED" "$COMMITTED" | sha256sum | cut -d' ' -f1)
>   SAVED=$(jq -r '.fingerprint // empty' "$REPO/.claude/.fable-gate.json" 2>/dev/null)
>   BY=$(jq -r '.by // empty' "$REPO/.claude/.fable-gate.json" 2>/dev/null)
>   [ "$FP" = "$SAVED" ] && echo "✅ 이 상태 판정 있음 (by=$BY)" || echo "⚠️ 미판정 변경 — 아래로 가른다"
> fi
> ```
> `⚠️` 이면 그 변경이 **공용 기준상 Fable 대상인가**를 가른다:
> - **대상**(돈·운영 DB·권한·공개 주소·외부 발송·삭제·보호 영역·계산·새 설계) → `/fable-검증` PASS 후 재개.
>   한도로 못 부르면 공용 기준 5절(자체 검증 숫자 · 상황판 Fable 대기 · `by:"unavailable"` 마커) — 개발완료는 계속하되 **운영 배포는 Fable 통과 뒤로**, 보고 첫 줄 `🕓 나중에 — Fable 대기: …`.
> - **대상 아님**(화면·문구·작은 버그·문서) → 자체 검증 숫자 + «Fable 미검증(자체 검증)» 으로 보고. 마커는 쓰지 않는다(다음 Fable 게이트가 이 커밋까지 같이 본다).
>
> ⚠️ **"변경 없음" 은 "검증했음" 이 아니다.** 커밋은 검증이 아니다 — 그래서 위 검사는 마지막 마커 이후 커밋까지 센다.

- health-check(런타임) + guard-invariants(정적 불변식 — mock/i18n·ko-en 패리티/무스코프 쿼리/notify·broadcast·costGuard·재무 owner/god-file 래칫) + e2e tenant(멀티테넌트 403 실증).
- guard-invariants 래칫 실패 = 신규 위반. 정리하거나, 의도된 부채 감소면 `--update-baseline` 후 재실행.

**판정:**
- 세 명령 모두 종료 코드 0 (통과) → 1단계로 진행
- 하나라도 0 아님 → **개발 완료 처리 중단.** 깨진 항목을 사용자에게 보고하고 복구 후 다시 `/개발완료` 실행.

이 단계의 목적: POS에서 겪은 "기능이 점점 깨지는 문제" 방지. 모든 신규/기존 기능이 정상이어야만 "완료" 인정.

### 7-B단계: 운영 피드백 안내 답변 (건너뛰기 금지)

> Irene 2026-10-07: *"개발완료 스킬에는 운영서버 피드백에서 완료한 것과 조치한 것에 대한 안내답변을 다 하게 하자."*

이번 세션에서 다룬 **모든** 운영 피드백(완료한 것 + 조치 중인 것)에 답글을 단다. 답글이 없으면
사용자에게는 "말해도 아무 반응이 없다" 이다 — 그리고 배포 스크립트(`close_feedback`)는 **답글 없는 건을 닫지 않는다.**

1. **대상 확정** — 운영에서 열린 건(`status IN ('pending','reviewing')`)을 다시 읽고(개발시작 1-B 와 같은 조회),
   이번 세션 커밋·session-state 의 피드백 번호와 대조한다. 원문 문장별로 ✅/❌ 를 매긴다.
2. **상태는 사실대로**
   | 상황 | status | 답글에 쓸 것 |
   |---|---|---|
   | 고쳐서 **운영 배포까지 끝남** | `done` | 무엇이 어떻게 바뀌었는지 · 어디서 확인하는지 |
   | 고쳤지만 **배포 전** | `reviewing` | 조치 내용 + "다음 배포에 반영됩니다" (배포 때 `Feedback-Closes:` 트레일러로 닫힌다) |
   | 일부만 해결 | `reviewing` | 된 것 / 남은 것을 나눠서 |
   | Irene 결정·외부 대기 | `reviewing` | 무엇을 기다리는지 |
   | 하지 않기로 함 | `wontfix` | 이유 (Irene 이 정한 것만) |
   - 원인이 사용자 환경(앱 재설치·재연결 등)이면 **사용자가 할 일**을 한 줄로 적는다.
   - 사용자 언어로 쓴다 — 파일명·함수명·커밋 해시 금지. 신고자의 언어(ko/en)로.
3. **적용** — 관리자 화면의 [답변] 과 같은 함수(`services/feedbackRespond`)를 쓰는 스크립트로 단다.
   답글은 보고자에게 **알림이 간다** — 그래서 먼저 dry-run 출력을 보고서에 싣고, 그다음 `--apply`.
   ```bash
   # replies.json: [{"id":457,"status":"reviewing","response":"…"}, …]
   scp replies.json irene@87.106.78.146:/tmp/fb-replies.json
   ssh irene@87.106.78.146 "cd /opt/planq/backend && node scripts/feedback-reply.js /tmp/fb-replies.json"           # dry-run
   ssh irene@87.106.78.146 "cd /opt/planq/backend && node scripts/feedback-reply.js /tmp/fb-replies.json --apply"   # 저장+알림
   ```
   ★ 운영에 `scripts/feedback-reply.js` 가 아직 없으면(이 스크립트가 배포되기 전) 이 단계는 **답글 초안만 보고서에 싣고**
     "배포 후 적용" 으로 남긴다. 운영 코드 디렉터리에 파일을 직접 넣지 않는다.
   멱등이다 — 같은 답글이 이미 있으면 건너뛴다(알림 중복 없음).
4. 보고서 "운영 피드백 답변" 절에 **번호 · 상태 · 답글 전문**을 싣는다.

완료 보고 전에 이번 세션의 실제 작업 주체별 변경을 기록합니다. 기록은 추정하지 말고 `git status`, `git diff --name-only`, `git diff --stat` 결과와 작업 로그를 대조합니다.

```markdown
### 작업 주체별 변경 기록
- [Claude Code] 조사·기획·설계·검증: [해당 시 기재]
- [Opus] Fable 설계 기반 핵심 구현: [해당 시 기재]
- [Codex] 지정된 단순·반복 작업: [해당 시 기재]
- [공동 검토] 대조·최종 판단: [해당 시 기재]

### Codex 자기 검증
- 실행 명령: `[Codex가 직접 실행한 명령]`
- 결과: [종료 코드와 핵심 결과]
- 검증 대상: [Codex 변경 파일]
```

- Codex가 변경한 파일이 있으면 Codex가 지정된 검증 명령을 직접 실행한 기록이 있어야 한다.

- 다른 AI의 미커밋 변경은 작업 주체 기록에 포함하되 덮어쓰거나 임의로 정리하지 않는다.
