## 이번 세션에서 배운 것 (재발 방지)

1. **★ "작동한다" 와 "사용자가 작동한다고 인지한다" 는 다르다.** 역방향 동기화는 몇 주째 정상이었는데
   신고는 계속됐다. 지연을 안 알려주면 사용자는 **기다림을 고장으로 읽는다**. 기능을 고친 뒤에는
   **그 사실이 화면에 도달하는 경로**까지가 작업 범위다.
2. **★ 신고가 반복되면 코드가 아니라 도달 경로를 의심하라.** 운영 데이터(감사로그·구글 API 현재값)로
   "이미 고쳐졌다" 를 먼저 증명하고 나서야 진짜 병인 3개가 보였다.
3. **★ 조치가 필요한 상태는 사용자가 그 문제를 겪는 화면에 있어야 한다.** 팀 토큰 사망 안내가
   설정 깊은 곳에만 있으면 없는 것과 같다.
4. **★ 권한 복구는 "연결"만으로 끝나지 않는다.** 죽어 있던 기간의 데이터가 목적지에서 빠져 있으면
   복구 후 첫 확인이 **비어 있다** → "역시 안 되네". 복구에는 **밀린 것 백필**이 따라와야 한다.
5. **★ 트리거를 한 화면에만 달면 다른 진입 경로에서 죽는다.** 백필을 캘린더 배너에서만 불렀더니
   설정 화면 재연결에서는 아예 안 돌았다. **모든 경로가 지나는 지점(서버 콜백)** 에 두는 것이 정합이다.
6. **★ broadcast 는 수신부까지가 기능이다.** 발신만 있고 듣는 곳이 0이면 "고쳤는데 화면은 아직
   고장이라고 말하는" 상태가 된다 — CLAUDE.md 16번 체크리스트가 정확히 이것을 막으려는 항목이다.
7. **★ 조건부 `return null` 은 언마운트가 아니라 cleanup 이 안 돈다** (memory `feedback_return_null_skips_cleanup`).
8. **★ 같은 목록·판정을 두 곳에 적으면 반드시 갈라진다.** health-check 카테고리 · needsReconnect ·
   개인 연동 판정 — 이번 사이클에만 3건이 나왔다. 정본 1벌 + fail-closed 검사로.
9. **★ 게이트가 깨지면 베이스라인을 올리지 말고 절출하라.** god-file 804줄을 `--update-baseline` 로
   삼키는 대신 훅으로 뺐더니, 덤으로 프론트/서버 판정이 갈라지던 곳도 하나로 합쳐졌다.
